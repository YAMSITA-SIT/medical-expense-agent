# 高額療養費Agent：バックエンド再構築

旧 `triage` の実行コードには依存しない。画面・国民向け入力フォームは作らない。ユーザーのP01〜P32を対応範囲の基準とし、登録済みと実装済みを区別する。

## 処理の責任

1. 信頼された接続処理が利用者・対象月を確定。DBから証拠付き資料と版を取得。
2. 決定的ルールで月額を算定。AI呼出しなしで終わる標準処理を優先。
3. 不足事実・矛盾・未実装ルールを別々に抽出。
4. 未解決時だけ、管理された行政資料の要約と審査skillを読み込む。
5. AIは許可された次の行動と照会案を選択。DBへの照会案保存を実行。国民・職員への送信は別の承認済み処理で行う。
6. 回答が証拠付きでDBへ追加されれば、再実行で古い照会案を失効し、新しい資料で再計算。

DBの事実、適用ルール、参照資料、skillの版を処理識別に含める。月額支給案は年間判定や正式決定と明確に分ける。資料内の命令をツール実行権限にしない。

## 実行

Node.js 24以上、追加パッケージ不要。

```
node benefit-agent/tests.mjs
node benefit-agent/demo.mjs
```

デモは架空資料を端末内SQLiteで処理。所得不足→職員照会案→回答保存→月額支給案→同一資料再実行を示す。実API呼出し・送信・振込は行わない。OrcaPlannerはAPIアダプターとして実装してあるが、実モデル検証は未実施。

## 現在の実装境界

- 月額算式：確認済みの同一国保世帯、75歳未満、標準所得区分。医療機関・医科歯科・入院外来・処方元薬局集計、世帯合算、年齢混在、多数回、現物給付・既支給控除。
- 明細はバックエンドが整理済みの内部事実を扱う。OCR・資料から事実を抽出するAIは未実装。
- 履歴は証拠と継続性が確認されたDB記録を消費。実支給システムからの同期は未実装。
- 申請期限は保険者の確認結果を消費。起算日・猶予等の自動判定は未実装。
- 例外の専用計算、後期高齢者・他保険、年間精算は未実装。全32パターン対応ではない。止めて職員へ渡せるだけでは対応完了としない。
- 新しい事実DBはSQLite。旧版Supabaseのデータ移行・利用者認証・権限管理・外部台帳接続は未実施。
- 行動選択の構造検証は文面の法的正確性を保証しない。実モデル評価が必要。

## 完了基準

各P01〜P32について、適用制度・施行期間、必要事実と取得先、該当・非該当条件、算式、例外遷移、根拠条項、公式例と境界値、訂正・再実行を対応付ける。関連パターンの複合条件も確認する。

DB参照→不足取得→再判定の一連の処理、資料更新時の再評価、二重照会・二重支給防止、職員承認・通知案までを実接続で検証して完了とする。LLMが金額を推測することや未対応を職員確認に送ることを、算式実装の代替にしない。


## 職員向けデモ（2026-09-20追加）

`npm start` で http://127.0.0.1:4176/ を起動。既存 triage/.env の Supabase 接続をサーバー側で使用します。新規テーブルは supabase.sql、初期データは npm run seed（既存案件は上書きしません）。

`npm test` は120件の検証、起動後の `node http-check.mjs` は実DBへの結合検証です。期待額は demo-tests.mjs に分離し、サーバーからインポートしません。

knowledge/originals にPDF原本、knowledge/sections.json に抽出本文。knowledge/ingest.mjs で非公開Storageと本文索引へ投入。現状は日本語2文字の全文検索で、ベクトルRAGではありません。

OrcaRouterは環境変数 ORCAROUTER_API_KEY、ORCAROUTER_MODEL を設定して起動。画面で送信内容を確認し、1回ごとに明示的に承認します。実サービスでの推論検証は未実施です。

32分類中、条件付き月額ルール18分類、不足確認1分類、専門算定未対応13分類。年間算定は未対応です。詳細は outputs/職員向けデモ・実装状況.md を参照してください。ケース単位JSON格納の開発用DBであり、本番の正規化済み台帳・認証を提供するものではありません。
